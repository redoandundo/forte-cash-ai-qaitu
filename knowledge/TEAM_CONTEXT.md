# Контекст команды Qaitu

## Кто мы

Qaitu — команда из трёх участников на мероприятии Datathon26. Мы решаем кейс ForteBank по анализу записей кассовой зоны.

Наша задача — создать полностью локальную систему компьютерного зрения, которая помогает проверяющему находить признаки возможных нарушений. Система должна показать, что наблюдалось, когда это произошло и какими кадрами подтверждается результат.

## Где мы участвуем

- Мероприятие: Datathon26.
- Кейс: ForteBank.
- Направление: локальный видеоанализ кассовых операций и контролируемой зоны.
- Репозиторий: `https://github.com/redoandundo/forte-cash-ai-qaitu`.
- Видимость репозитория: public; публикуются только безопасные код и документация.
- Командная ветка разработки: `develop`.
- Стабильная ветка: `main`.

## Что мы создаём

```text
кассовое видео
  -> локальное декодирование
  -> временные окна
  -> видео-модель
  -> scores и события
  -> таймкоды
  -> JPEG evidence
  -> API-результат для ручной проверки
```

Результат формулируется как «обнаружены признаки возможного нарушения». Команда не строит систему автоматического юридического решения.

## Состав команды

### Тимлид и архитектор

Основная ответственность:

- общая архитектура;
- GitHub и правила веток;
- API и job lifecycle;
- общие contracts;
- безопасность данных;
- интеграционные тесты;
- финальная сборка и demo Datathon26;
- frontend, публичный URL и точное соответствие API жюри;
- принятие handoff двух участников.

Ветка: `feature/teamlead-core`.

Основные пути:

- `src/api/**`;
- `src/jobs/**`;
- `src/core/**`;
- `tests/api/**`;
- `tests/integration/**`;
- `.github/**`;
- общие файлы архитектуры и контекста.

Тимлид не должен одновременно становиться владельцем всех ML-экспериментов и внутренней реализации video pipeline. Его задача — зафиксировать границы и соединить проверенные компоненты.

### Участник 1 — ML-инженер

Основная ответственность:

- аудит и подготовка датасета;
- duplicate-safe train/validation split;
- R3D-18 baseline;
- эксперимент X3D-XS, если окружение стабильно;
- обучение и оценка;
- precision, recall, F1, confusion matrix и error analysis;
- экспорт ONNX или согласованного TorchScript;
- parity и smoke tests;
- model manifest, preprocessing, thresholds и checksum;
- handoff для inference-инженера.

Ветка: `feature/ml-model`.

Основные пути:

- `src/ml/**`;
- `configs/ml/**`;
- `tests/ml/**`;
- `reports/ml/**`;
- `docs/handoffs/ml-to-inference.md`.

ML-инженер не меняет API, jobs и video pipeline без согласования.

### Участник 2 — inference-инженер

Основная ответственность:

- metadata и streaming decode `.mov`;
- корректные временные метки;
- temporal windows и sampling;
- `MockPredictor` для независимой разработки;
- `OnnxPredictor` с CPU/GPU providers;
- temporal aggregation;
- timecodes и 1–3 JPEG evidence;
- benchmark времени, RAM и VRAM;
- подключение экспортированной модели;
- handoff для тимлида.

Ветка: `feature/video-inference`.

Основные пути:

- `src/inference/**`;
- `configs/inference/**`;
- `tests/inference/**`;
- `reports/inference/**`;
- `docs/handoffs/inference-to-teamlead.md`.

Inference-инженер не обучает конкурирующую модель и не меняет публичный API.

## Как участники зависят друг от друга

```text
ML-инженер
  -> model contract
  -> model artifact + manifest + checksum
  -> ML handoff
       |
       v
Inference-инженер
  -> ONNX adapter
  -> events + timecodes + evidence
  -> inference handoff
       |
       v
Тимлид
  -> API + jobs + integration tests
  -> demo release
```

Пока ML-модель не готова, inference-инженер работает с `MockPredictor`. Поэтому две ветки развиваются параллельно.

## Модельная стратегия

- R3D-18 — обязательный baseline первого участника.
- X3D-XS — сравнительный кандидат.
- Второй участник не скачивает pretrained модели на первом спринте: он получает готовый export.
- RT-DETR и ByteTrack рассматриваются только после error analysis и отдельного решения.
- SmolVLM2 остаётся исследовательским компонентом и не входит в обязательный production path.

## Общая integration-ветка

`integration/ml-inference` используется только для соединения ML и inference до попадания в `develop`.

Порядок:

1. Оба участника работают в своих feature-ветках.
2. ML-инженер публикует contract и handoff.
3. Тимлид принимает проверенный ML результат в integration.
4. Inference-инженер подключает artifact и публикует свой Draft PR в integration.
5. Команда выполняет end-to-end tests.
6. Тимлид продвигает integration в `develop`.
7. Проверенная demo-сборка продвигается из `develop` в `main`.

## Как команда использует Codex

У каждого участника есть Codex и мощное локальное железо. Codex получает командный контекст не из пересказов в чатах, а из репозитория:

- `AGENTS.md` — обязательные правила;
- `GOALS.md` — цели и non-goals;
- `PLANS.md` — текущая фаза;
- `knowledge/` — команда, архитектура и статус;
- `docs/contracts/` — интерфейсы;
- `docs/handoffs/` — передача результата;
- `docs/team/` — подробные инструкции участникам;
- `codebase-memory-mcp` — локальный граф актуального кода.

Каждый Codex должен сначала читать эти источники, а затем работать только в зоне своей роли.

## Командные правила

- Один владелец у каждого компонента.
- Маленькие проверяемые commits.
- Никаких прямых commits в `main`, `develop` и integration.
- Никаких видео, весов, evidence и секретов в обычном Git.
- Никакого исходного PDF, dataset labels и подробных dataset-derived обзоров в публичном Git.
- Любой результат сопровождается командой воспроизведения.
- Нельзя объявлять тест или benchmark выполненным без фактического запуска.
- Техническая ошибка не является `no_violation`.
- Неподтверждённое наблюдение не превращается в юридическое утверждение.
- Контракт меняется только с уведомлением downstream-участника и review тимлида.

## Определение общего успеха

Команда готова к финальной демонстрации, когда:

1. модель воспроизводимо обучена и экспортирована;
2. pipeline анализирует полное видео и возвращает события;
3. API создаёт job и выдаёт результат;
4. публичный API использует `X-API-Key`, статусы `processing/done/failed` и verdict `violation/no_violation`;
5. timecodes соответствуют фактическим событиям;
6. 1–3 JPEG evidence возвращаются в base64;
7. обработка локальна и укладывается в 300 секунд;
8. frontend и API доступны по публичному URL;
9. demo запускается по одной документированной инструкции;
10. известные ограничения честно описаны.
