# Upload-first UI shell для демо Qaitu

Дата: 17 октября 2026 года

Статус: утверждено пользователем и реализовано в UI-болванке

## Цель

Собрать приятную для ручной проверки интерфейсную болванку Qaitu без зависимости от ML-модели и полноценного inference. Начальный экран не показывает готовый кейс: пользователь сначала выбирает локальный `.mov`, после чего получает рабочее пространство с превью и управляемыми демо-состояниями.

## Основной сценарий

1. Пользователь открывает приложение и видит название продукта, краткое объяснение локальной обработки и крупную область загрузки.
2. Пользователь перетаскивает `.mov` в область загрузки или выбирает файл через системный диалог.
3. Браузер создаёт локальный object URL и показывает превью, имя и размер файла. Файл не отправляется во внешние сервисы.
4. Пользователь нажимает кнопку запуска проверки.
5. UI переходит в состояние обработки, а затем позволяет воспроизводить согласованные демо-состояния без модели.
6. Пользователь может заменить видео и вернуться в исходное состояние.

## Начальный экран

- Пустой upload-first экран без результатов, событий и заранее заполненного кейса.
- Главный акцент — drag-and-drop зона с кнопкой «Выбрать видео».
- Рядом с загрузкой указываются формат `.mov`, лимит размера и факт локальной обработки.
- API-ключ не занимает место в основном сценарии. Технические параметры находятся в сворачиваемом блоке «Технические настройки».
- Текст не обещает юридический вывод и не называет результат автоматическим решением.

## Рабочее пространство после выбора файла

Интерфейс меняется без перехода на отдельную страницу:

- слева находится видеоплеер с выбранным локальным файлом;
- рядом показываются имя, размер и кнопки «Начать проверку» и «Выбрать другое видео»;
- справа или ниже, в зависимости от ширины экрана, находится панель статуса;
- переключатель демо-состояний появляется только после выбора файла и помечается как инструмент демонстрации;
- при замене файла предыдущий object URL освобождается.

## Демо-состояния

Интерфейс должен позволять вручную проверить пять состояний:

1. `ready` — файл выбран, проверка ещё не начата;
2. `processing` — показан прогресс локальной обработки;
3. `violation` — показаны признаки возможного нарушения, таймкод и карточка evidence;
4. `no_violation` — показано осторожное сообщение «признаки не обнаружены в этой записи»;
5. `failed` — техническая ошибка отделена от отрицательного verdict и содержит понятное действие для повторной попытки.

Тестовые результаты существуют только во frontend mock-слое. Обязательный публичный API-контракт не меняется.

## Визуальное направление

- Внутренний банковский инструмент, а не маркетинговый лендинг.
- Интерфейс строится в актуальной палитре Forte: основная маджента, глубокий бордово-пурпурный, мягкие розовые оттенки и светлые нейтральные поверхности. Основание направления — [официальное сообщение Forte о ребрендинге](https://forte.kz/ru/news/press-reliz).
- Основные действия, focus-ring, drag-over и активные элементы используют Forte magenta. Тёмный пурпурный применяется для текста и контрастных поверхностей, а светлый розовый — для ненавязчивой подсветки.
- Зелёный остаётся только семантическим цветом успешного результата, красный — ошибки или риска; они не конкурируют с фирменной маджентой.
- Точные HEX-токены считаются частью реализации прототипа и должны быть собраны в `:root`, чтобы их можно было быстро заменить после получения официального brand kit.
- Светлый фон, компактная типографика и высокий контраст сохраняют читаемость интерфейса.
- Чёткие состояния focus, hover, drag-over, disabled и error.
- Умеренные радиусы и тени; декоративные эффекты не должны конкурировать с видео и статусом.
- На узком экране рабочие панели складываются вертикально, а основные действия остаются доступными без горизонтальной прокрутки.

## Поведение и безопасность

- На первом экране нет фиктивных данных.
- Пользовательский текст вставляется через безопасные DOM API; шаблонные mock-данные контролируются приложением.
- Выбранное видео остаётся локальным до явного запуска реального backend-сценария.
- Ошибка воспроизведения `.mov` показывается отдельно от ошибки анализа.
- Статус `failed` никогда не отображается как `no_violation`.
- Интерфейс использует формулировку «признаки возможного нарушения».

## Архитектура frontend

- `web/index.html` содержит семантические области загрузки, workspace, статуса и технических настроек.
- `web/styles.css` задаёт токены, адаптивную двухколоночную компоновку и состояния компонентов.
- `web/app.js` управляет выбранным файлом, object URL, состоянием UI и mock fixtures.
- Реальный API-клиент остаётся отдельным путём и не смешивается с генерацией mock-результатов.
- Mock-режим можно будет удалить или отключить без изменения HTML-контракта основных компонентов.

## Проверка

Минимальная приёмка интерфейсной болванки:

- исходный экран не содержит демо-кейса;
- файл можно выбрать и перетащить;
- выбранное видео отображается локально, когда кодек поддерживается браузером;
- замена файла очищает предыдущий preview URL;
- все пять демо-состояний переключаются без backend и модели;
- `failed` визуально и семантически отличается от `no_violation`;
- интерфейс остаётся пригодным при ширине 375 px;
- базовый backend API и его публичная JSON-схема не изменены.

## Вне scope

- реальное ML/inference;
- автоматическое определение события по видео;
- сохранение истории проверок;
- недельный дашборд и досье;
- публикация внешнего URL;
- изменение контрактов в `docs/contracts/`.
