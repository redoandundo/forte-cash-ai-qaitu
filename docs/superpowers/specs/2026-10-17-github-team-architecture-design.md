# GitHub-архитектура команды ForteBank Video Compliance

Дата: 2026-10-17

Статус: утверждено для оформления

Владелец архитектуры: тимлид

## 1. Цель

Организовать пустой GitHub-репозиторий для команды из трех человек так, чтобы:

- тимлид владел системной архитектурой, API, jobs и релизом;
- ML-инженер независимо обучал и экспортировал модель;
- inference-инженер независимо создавал видео pipeline;
- незавершенные ML и inference-компоненты соединялись во временной integration-ветке;
- Codex каждого участника получал одинаковый устойчивый контекст из репозитория;
- видео, секреты, веса и runtime-артефакты не попадали в обычную историю Git.

## 2. Принятое решение

Использовать модель `main -> develop -> feature branches -> integration -> develop -> main`.

```text
main
└── develop
    ├── feature/teamlead-core
    ├── feature/ml-model
    ├── feature/video-inference
    └── integration/ml-inference
```

Ветки `feature/*` создаются от `develop`. Ветка `integration/ml-inference` также создается от `develop` и принимает Draft PR двух технических участников. После end-to-end проверки integration-ветка вливается в `develop`. Релизный PR идет из `develop` в `main`.

## 3. Зависимость ML и inference

Inference-инженер не ответвляется от незавершенной ML-ветки. Общая зависимость выражается контрактом модели, который находится в базовой структуре репозитория.

До появления реального артефакта используется `MockPredictor`. После передачи модели меняется только реализация `OnnxPredictor`, а декодирование, windowing, aggregation и evidence остаются неизменными.

## 4. Модельная стратегия

- R3D-18 — обязательный воспроизводимый baseline ML-инженера.
- X3D-XS — сравнительный кандидат ML-инженера, если окружение стабильно.
- Inference-инженер не обучает и не скачивает эти pretrained weights: он получает экспортированный ONNX/TorchScript и manifest.
- RT-DETR и ByteTrack разрешаются только отдельным архитектурным решением после error analysis.
- SmolVLM2 является исследовательским компонентом и не входит в основной production path.
- До handoff второй участник использует только MockPredictor и маленький локальный test fixture.

## 5. Контекст для Codex

Источником истины являются текстовые файлы, доступные Git diff и code review:

- `AGENTS.md` — долговременные правила и границы;
- `GOALS.md` — цели и non-goals;
- `PLANS.md` — фазы и зависимости;
- `PROMPTS.md` — повторно используемые prompts;
- `knowledge/` — архитектура, глоссарий и текущее состояние;
- `docs/contracts/` — интерфейсы между участниками;
- `docs/handoffs/` — воспроизводимая передача результатов;
- локальный `codebase-memory-mcp` — производный граф фактического кода.

Кэш графа MCP не коммитится. Центральный `knowledge/current_state.yaml` обновляет тимлид; участники обновляют только собственные handoff-файлы.

## 6. Хранение модели

В Git коммитятся код, manifest, preprocessing, thresholds, labels, checksum и инструкция запуска. Большие веса передаются через согласованное приватное хранилище, Git LFS или приватный GitHub Release. Исходные видео и evidence в GitHub не загружаются.

## 7. Контроль качества

В `main` и `develop` запрещены прямые push. Обязательны PR, автоматические тесты и отсутствие unresolved conflicts. В `integration/ml-inference` разрешены только контролируемые объединения feature-веток и минимальный integration glue.

## 8. Полное руководство

Команды, дерево репозитория, правила ownership, model handoff и точный prompt для Codex второго участника находятся в:

`docs/team/GITHUB_TEAM_ARCHITECTURE.md`

## 9. Самопроверка спецификации

- У структуры есть единственная стабильная release-ветка.
- У каждого участника одна основная зона владения.
- Зависимость ML -> inference выражена контрактом, а не общей рабочей веткой.
- Большие и чувствительные данные исключены из обычного Git.
- Источники контекста имеют однозначных владельцев.
- Процедура integration не требует переписывать историю опубликованных веток.
- Неопределенные GitHub usernames не зафиксированы: они подставляются при настройке CODEOWNERS.
