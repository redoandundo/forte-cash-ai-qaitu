# Дизайн улучшения ForteBank Video Audit под критерии Datathon 26

## Назначение

Цель проекта — превратить текущий исследовательский ML baseline в полностью локальный сервис, который максимизирует итоговый балл по семи критериям Datathon 26, а не только одну бинарную метрику. Сервис должен принимать MOV через веб-интерфейс и API, за пять минут выдавать вердикт по ролику, локализованные события, проверяемые кадры, осторожный тип наблюдаемого события и связь с официальным нормативным источником Республики Казахстан.

Главный текущий дефект — рабочий API использует старый `artifacts/baseline.joblib`, хотя более сильная MobileNet ONNX-модель уже подготовлена. Поэтому фактическое демо не соответствует ML-отчётам. Кроме того, API всегда возвращает общий тип события и не показывает нормативный источник. Это напрямую снижает баллы за качество обнаружения, классификацию и обоснованность правил.

## Критерии успеха

| Критерий Datathon | Вес | Проверяемый результат проекта |
|---|---:|---|
| Качество обнаружения | 25 | Scenario-safe nested OOF без утечки; основной ориентир — macro F1, при выборе порога recall не ниже 0.75 и минимально возможное число ложных тревог |
| Качество локализации | 15 | Для положительных роликов timestamp MAE ниже текущих 8.48 с и не менее 65% событий в пределах ±5 с; 1–3 релевантных кадра |
| Качество классификации | 15 | Небольшая проверяемая таксономия визуальных событий, open-set fallback для неизвестного типа и OOF-оценка по подтверждённым типам |
| Обоснованность правил | 15 | Только официальные источники РК; у события есть документ, раздел или пункт, URL и формулировка без юридического утверждения сверх видимого |
| Устойчивость | 10 | Сохранение пропорций кадра, геометрические и фотометрические augmentations, отдельные тесты на изменение угла и ориентации |
| Готовность продукта | 10 | Реальный ONNX inference в API, понятный UI, надёжная обработка ошибок, загрузка MOV до 100 МБ, результат менее чем за 5 минут |
| Техническое решение | 10 | Полностью локальный воспроизводимый pipeline, ONNX parity, manifest и checksum, документированные ограничения и возможность добавления новых типов |

Текущий доказанный baseline для promotion — nested OOF на 40 уникальных источниках: macro F1 `0.540`, recall `0.667`, false positives per negative minute `0.874`, timestamp MAE `8.48 с`, попадание в ±5 с `52.4%`. Новый кандидат сравнивается на тех же folds и с независимо откалиброванным порогом. Для promotion он не должен ухудшить macro F1, recall или false positives per minute и должен заметно улучшить хотя бы одну из трёх областей: обнаружение, локализацию или устойчивость. При близких значениях выбирается более компактная и быстрая модель.

## Предлагаемая система

### 1. Единый inference контур

API загружает ONNX-модель и метаданные один раз при старте. Видео разбивается на шестисекундные окна с шагом две секунды. Каждое окно получает score; последовательность сглаживается, а соседние превышения порога объединяются в события. Техническая ошибка никогда не превращается в `no_violation`.

Первым рабочим кандидатом становится существующая `mobilenet-temporal-pairsafe-v3`, подключённая к API вместо старого HOG и logistic regression baseline. Она остаётся fallback, пока новый кандидат не пройдёт те же nested OOF gates.

Group identity уже определён в датасете: точные дубликаты объединяются по SHA-256 полного исходного видео, а визуально связанные положительные и отрицательные постановки объединяются по `scenario_group`. Производные clips и разные таймкоды одного источника никогда не расходятся между train, calibration и outer evaluation.

Обязательный API-контракт фиксируется по кейсу: `POST /api/v1/analyze` принимает поле `file` и возвращает `job_id`; `GET /api/v1/jobs/{job_id}` возвращает `processing`, `done` или `failed`. Успешный результат содержит `verdict` со значением `no_violation` или `violation` и список `violations`. Каждое событие содержит `type`, `timecode_sec`, `description` и 1–3 объекта `evidence_frames` с `timestamp_sec` и JPEG в base64. Несколько разделённых событий возвращаются отдельными элементами списка.

### 2. Модель временных событий

Основной новый кандидат — компактная point-supervised temporal MIL модель:

- MobileNetV3 извлекает embedding для каждого окна с сохранением пропорций изображения через letterbox;
- лёгкая temporal head обрабатывает последовательность embeddings всего ролика;
- video loss учит общий вердикт;
- timestamp loss мягко усиливает окна рядом с размеченным таймкодом с учётом confidence разметки;
- sparsity и smoothness losses формируют короткие устойчивые события;
- hard-negative peak loss подавляет самые уверенные ложные окна отрицательных роликов;
- scenario-pair ranking используется только как дополнительный loss с малым весом, потому что отдельный эксперимент с весом 0.5 уже ухудшил nested OOF macro F1 с 0.540 до 0.479.

Embeddings кэшируются локально, поэтому temporal head можно быстро переобучать и проверять на пяти folds. Кандидат заменяет текущую ONNX-модель только при улучшении честной nested OOF оценки и отсутствии регрессии по false positives, recall, latency и ONNX parity.

Ground truth локализации — один или несколько точечных таймкодов внутри уникального source. Для обучения вокруг каждого таймкода строится мягкая временная цель. Для оценки предсказанные и истинные события сопоставляются один-к-одному по минимальному временному расстоянию; unmatched предсказания считаются лишними событиями, unmatched истинные события — пропусками. Это не позволяет одному удачному пику закрыть несколько событий.

### 3. Типы событий

Поскольку официальный датасет содержит только бинарную метку и таймкод, сначала проводится визуальная ревизия 21 положительного уникального источника. Для каждого события сохраняются:

- только наблюдаемое действие;
- кандидатный тип;
- confidence `high`, `medium` или `low`;
- связанный нормативный источник или отметка, что связь не подтверждена.

Из подтверждённых примеров формируется малое число типов. Классификация строится как nearest-prototype по embedding события и проверяется source-safe OOF. Если сходство недостаточно или тип отсутствовал в обучении, сервис возвращает нейтральный тип `Иное визуально наблюдаемое событие`, не выдумывая конкретное нарушение.

Таксономию и нормативное соответствие формирует команда, как прямо допускает кейс; экспертной разметки ForteBank нет. Поэтому каталог разделяет наблюдение, кандидатный тип и нормативную интерпретацию, хранит confidence и не использует неподтверждённые примеры как эталонные prototypes.

### 4. Доказательства и нормативная связь

Для каждого события сервис выбирает до трёх кадров: до пика, на пике и после пика. Описание разделяется на две части: что непосредственно видно и почему фрагмент направлен на проверку человеком. Нормативный каталог хранится в локальном JSON и содержит название акта, орган, пункт или раздел, официальный URL, дату проверки и допустимую осторожную формулировку.

В API сохраняются все обязательные поля кейса. Дополнительный объект `rule` добавляется обратно совместимо; обязательные данные также кратко отражаются в `description`, чтобы проверяющий не потерял связь, если его клиент игнорирует дополнительные поля.

### 5. Устойчивость и продуктовый контур

Предобработка перестаёт растягивать вертикальное видео в квадрат. Добавляются letterbox, умеренные perspective и rotation transforms, brightness, blur, compression и тестовый набор преобразований, имитирующих другой угол. Для финального ролика под новым углом используется тот же локальный pipeline без дообучения на тесте.

API валидирует реальную декодируемость MOV, размер и длительность, ограничивает параллелизм, удаляет временные файлы и хранит состояния заданий с TTL. Health endpoint сообщает готовность модели и её версию. UI показывает статус, вердикт, тип, три evidence frames, наблюдение, нормативный источник и предупреждение о необходимости человеческой проверки.

Локальный performance target проверяется на имеющемся ноутбуке с RTX 3050 Ti и на CPU fallback для ролика длительностью до 145 секунд. На обоих путях действует жёсткий внешний лимит пять минут. Число одновременных GPU-анализов ограничивается одним, остальные задания стоят в очереди. Окончательная конфигурация публичного хоста должна быть не слабее подтверждённой целевой среды либо пройти тот же benchmark перед сдачей.

## Этапы реализации

1. Подключить существующую ONNX-модель к API и зафиксировать end-to-end контракт.
2. Добавить тесты API, inference, evidence frames, ошибок декодирования и пятиминутного бюджета.
3. Провести визуальную ревизию положительных событий и создать версионированную таксономию с confidence.
4. Добавить официальный нормативный каталог и безопасные шаблоны объяснений.
5. Реализовать кэш embeddings и temporal MIL head.
6. Запустить ablation и nested OOF эксперименты; продвигать только лучший доказанный кандидат.
7. Улучшить UI и подготовить воспроизводимый пакет запуска, демонстрационный сценарий и честный model card.

## Не входит в проект

- распознавание или идентификация лиц;
- облачные AI API и передача видео наружу;
- утверждение о юридически доказанном нарушении;
- типы событий без наблюдаемых признаков и проверяемого основания;
- обучение на финальных тестовых видео;
- тяжёлая модель, которая не укладывается в пятиминутный бюджет или недоступна на ресурсах команды.

## Защита от провала

Проект считается неудачным, даже если локальная метрика выросла, когда есть scenario leakage, порог выбран на evaluation fold, тип события выдуман, нормативная ссылка не подтверждена, API использует другой артефакт, чем отчёт, либо ошибка анализа возвращается как отсутствие нарушения. Все такие случаи блокируют promotion модели.

## Решения, оставленные реализации

Конкретная ширина temporal head, размер embedding, веса вспомогательных losses, число prototype типов и пороги open-set выбираются по nested OOF и latency. Конкретный формат дополнительного поля `rule` может быть плоским или вложенным, если обязательный JSON-контракт из кейса остаётся совместимым.
